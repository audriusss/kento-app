2. PRODUCTION READINESS FOR 100 USERS
==================================================

Audit the existing architecture for:

- 100 registered users
- 10–20 simultaneously active voice users
- a possible burst of up to 100 simultaneous requests

Do not over-engineer or introduce Kubernetes, microservices, or unnecessary infrastructure.

Inspect the actual code and determine:

A. API KEY SECURITY

Verify that:

- OpenAI API keys are not bundled inside the Android APK
- no secret is present in BuildConfig, strings.xml, source code, or client-visible network requests
- secrets exist only on the backend
- Android communicates with our backend rather than directly exposing privileged provider credentials

If the Android client currently contains a provider secret, report it as a critical issue and move privileged requests behind the backend without breaking the current user flow.

B. USER AND SESSION ISOLATION

Verify that every request has a stable user/device/session identifier.

Ensure:

- one user’s conversation context cannot mix with another user’s
- transcription uploads are associated with the correct session
- navigation state is never stored globally on the server
- server-side mutable singleton state is not shared between users
- conversation history has bounded size and expiration

C. RATE LIMITING

Add simple backend rate limiting where missing.

Protect:

- transcription endpoint
- AI chat endpoint
- TTS endpoint, if server-based
- authentication or device-registration endpoint

Use sensible limits and return clear HTTP 429 responses.

Avoid blocking normal driving conversation.

D. REQUEST LIMITS

Enforce:

- maximum audio upload size
- maximum audio duration where available
- accepted MIME types
- request timeout
- AI response timeout
- maximum prompt/history length
- maximum generated response length

Reject invalid requests before sending them to external AI providers.

E. CONCURRENCY AND PERFORMANCE

Check whether the backend:

- blocks the Node.js event loop
- reads large audio files fully into memory unnecessarily
- uses synchronous filesystem operations in request handlers
- stores temporary files without deleting them
- has a concurrency bottleneck or global mutex
- has safe HTTP client connection and timeout settings

For the target scale, prefer streaming or bounded buffers where practical, but do not redesign working code without evidence.

F. FAILURE HANDLING

Ensure:

- provider timeout produces a controlled response
- provider 429 is handled
- provider 500/503 is handled
- Android receives a useful retryable error
- duplicate mobile retries do not accidentally create duplicate AI responses
- failed temporary uploads are cleaned up
- no request waits forever
