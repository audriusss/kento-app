TASK: Full end-to-end stabilization audit for Kentas navigation.

GOAL

Make the complete navigation flow reliable from destination entry to arrival on a real Xiaomi device.

This is a stabilization and repair task.
Do not add new product features.
Do not redesign the UI.
Do not change the visual settings screen.
Do not remove Android Geocoder unless an already-configured replacement fully covers the same path.
Do not push automatically.

REAL-DEVICE FAILURES TO INVESTIGATE

1. Voice listens but sometimes gives no spoken response.
2. Address can work on the first trip, then later resolve incorrectly or produce nonsense.
3. Current location marker is visible, but:
   - route line may be missing;
   - turn arrows/instructions may be missing;
   - left/right guidance may not appear;
   - map may look only partially loaded.
4. Starting a second trip after completing or cancelling the first is less reliable.
5. While driving, the phone screen dims or turns off.
6. Typed destination and spoken destination must behave identically.
7. Navigation must remain functional from:
   - app launch
   - destination entry
   - destination resolution
   - route calculation
   - guidance start
   - driving
   - rerouting
   - arrival
   - starting another trip

Do not patch blindly.

PHASE 3 — FIX VOICE LISTENS BUT DOES NOT SPEAK

Audit the complete TTS state machine.

Verify:

- TTS initialization success/failure is observable.
- No call to speak occurs before initialization.
- Every deterministic navigation response reaches ttsManager.speak().
- AI/casual responses also reach the same TTS path.
- Empty/null responses are handled explicitly.
- notifyCommandDone or recognizer restart does not happen before TTS begins.
- SpeechRecognizer is not listening over TTS and immediately swallowing the response.
- TTS callbacks always release the voice session.
- TTS errors recover the continuous-listening loop.

Required behavior:

1. Recognize command.
2. Stop/pause listening.
3. Build response.
4. Call TTS.
5. Wait for onDone/onError.
6. Restart listening exactly once.

Never leave UI permanently in:
- "Kentas klauso"
- "Kentas galvoja"
- speaking state

Add a timeout fallback for a missing TTS callback, but do not use arbitrary delays as the normal path.

PHASE 4 — FIX NAVIGATION AND MAP STATE

Audit navigator and NavigationView ownership.

Verify:

- Navigator is not destroyed when a Compose screen temporarily disposes.
- NavigationView lifecycle callbacks match Activity lifecycle.
- onViewDestroy and full navigator onDestroy are not confused.
- The same active Navigator instance is used by:
  - setDestinations
  - startGuidance
  - route listeners
  - instruction listeners
  - NavigationView
- Listeners are registered once and removed correctly.
- A second trip does not reuse stale destination, route token, listener, or UI state.
- stop navigation resets only trip state, not the entire engine unless required.
- startGuidance is called only after route calculation succeeds.
- route errors are surfaced to TTS/UI.
- loading state cannot remain stuck.

Create an explicit minimal navigation state machine if one is not already present:

IDLE
RESOLVING_DESTINATION
CALCULATING_ROUTE
ROUTE_READY
GUIDING
ARRIVED
FAILED
STOPPED

Transitions must be deterministic and logged.

Prevent stale async callbacks from an older route attempt from modifying a newer attempt. Use attempt IDs or generation tokens.

PHASE 5 — TURN ARROWS AND MANEUVER INSTRUCTIONS

Find why current location can be visible while turn guidance is absent.

Verify:

- guidance is actually active;
- route exists;
- maneuver/instruction listener is attached;
- navigation UI is bound to the active Navigator;
- camera/navigation-follow mode is enabled when guidance begins;
- UI state receives current maneuver updates;
- instructions are cleared only on arrival/stop, not during recomposition;
- rerouting preserves listener bindings.

If Google Navigation UI should render arrows automatically, confirm all required lifecycle and binding calls are executed.

Do not create fake turn arrows manually if the SDK should supply them.

PHASE 6 — SECOND TRIP / SAME SESSION

This must be tested explicitly.

Scenario:

1. Launch app.
2. Navigate to address A.
3. Stop or arrive.
4. Enter address B.
5. Start navigation again.

Audit and fix:

- stale route
- stale destination
- stale attempt ID
- guidance already started flag
- listener duplication
- disposed NavigationView
- destroyed Navigator
- old TTS/voice jobs
- old current-city context
- loading/error state not reset

The second trip must work without restarting the app.

PHASE 7 — KEEP SCREEN ON WHILE NAVIGATING

While guidance is active, the display must not dim or turn off.

Implement using the correct Android mechanism:

Preferred:
- Activity window FLAG_KEEP_SCREEN_ON while navigation state == GUIDING

or:
- Compose Modifier.keepScreenOn equivalent if already used safely

Rules:

- enable when active guidance starts;
- keep enabled during rerouting and normal driving;
- disable on arrival;
- disable on stop/cancel;
- disable when leaving the navigation flow;
- avoid permanent wake lock;
- do not request unnecessary WAKE_LOCK permission if FLAG_KEEP_SCREEN_ON is sufficient.

Log screen-on state transitions under KentasLifecycle.

PHASE 8 — LOCATION AND DESTINATION CONSISTENCY

Preserve the current city-scoped resolver logic.

Verify:

- typed and spoken address share the exact same resolver;
- fresh location is used;
- stale location is rejected;
- city cache is invalidated correctly;
- another-city result is rejected;
- no nationwide fallback occurs silently;
- destination coordinates passed to Navigation SDK are exactly the accepted result.

Add the accepted destination name and coordinates to KentasNavigation logs before setDestinations.

PHASE 9 — ERROR RECOVERY

Every failure must produce a clear UI/TTS result and return to a usable state.

Cover:

- no speech result
- TTS initialization failure
- address not found
- city unknown
- location permission missing
- stale/unavailable location
- route calculation failure
- network unavailable
- Navigation SDK error
- map/navigation view not ready
- second-trip stale callback
- user cancels during route calculation

No infinite spinners.
No silent failures.
No permanent disabled microphone.
No need to restart the app after an error.
