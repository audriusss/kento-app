You are refactoring an existing Android application called “Šturmanas Bajeristas / Kentas”.

This is a deliberate product simplification, not another patch on top of the existing voice state machine.

FIRST inspect the entire current project, understand the existing navigation implementation, and identify which parts already work. Preserve the working Google Navigation SDK route/navigation integration. Then refactor the application to the architecture and behavior described below.

Do not blindly delete working navigation code.
Do not add multiple modes, personalities, humor levels, or voice profiles.
There is exactly ONE Kentas.

==================================================
PRODUCT GOAL
==================================================

The application must be a simple navigation app with one AI companion named Kentas.

Kentas is always the same character:

- Lithuanian-speaking
- natural, informal, friendly
- talks like a normal guy sitting in the passenger seat
- knows general information
- can hold a conversation
- jokes and may use tasteful dark humor
- does not sound like a formal robot
- does not have selectable personalities or humor levels
- does not have separate “navigation Kentas” and “AI Kentas”

The application has one stable navigation flow and one optional conversation interaction.

==================================================
CORE USER FLOW
==================================================

1. User opens the application.
2. The app immediately requests/reads the current GPS location.
3. The current location is displayed on the map.
4. The user enters the destination manually using the text/address field.
5. No voice destination input exists.
6. The user selects a valid destination and starts the route.
7. Google Navigation SDK starts guidance from the latest current location.
8. The screen remains awake while navigation is active.
9. Kentas provides navigation instructions in his own natural Lithuanian style.
10. The user can press one Kentas/microphone button to start a conversation.
11. After 30 seconds without user speech, the conversation listening session ends.
12. The app returns to normal navigation-only behavior.
13. Navigation must continue uninterrupted during conversation.

==================================================
ONLY TWO FUNCTIONAL STATES
==================================================

The UI and architecture may internally use simple state, but the user must only experience:

A. NAVIGATION

- route remains active
- map remains visible
- Kentas speaks navigation instructions when required
- microphone is not constantly listening
- no automatic SpeechRecognizer restart loops

B. KENTAS CONVERSATION

- entered only when the user presses the Kentas/microphone button
- microphone listens for the user
- recognized text is sent to the existing AI/OpenAI integration
- Kentas answers through TTS
- conversation can continue naturally
- each user interaction resets the inactivity timer
- after 30 seconds with no detected user speech, stop listening and return to navigation behavior
- conversation may also be manually closed by pressing the same button

Do not create additional visible modes.

==================================================
REMOVE THE OLD VOICE COMPLEXITY
==================================================

Completely remove or retire the old logic that causes voice instability, including where applicable:

- voice destination/address collection
- automatic voice activation when navigation starts
- application-wide continuous listening
- automatic endless SpeechRecognizer restart loops

- FINALIZING / RESTART_WAIT-style orchestration where no longer required
- multiple voice modes

- duplicated session booleans controlling the same feature

- stale callbacks that start a new recognizer session after conversation has ended

Do not preserve obsolete logic merely because tests currently depend on it.
Update or remove obsolete tests.

SpeechRecognizer must only be active while the user explicitly has the Kentas conversation open.

Do not use SpeechRecognizer for entering a destination.

==================================================
NAVIGATION

Use the existing working Google Navigation SDK integration.

Requirements:

- manually entered destination only

- start route guidance reliably

- route must survive opening and closing the Kentas conversation
- stop-navigation control must remain available
- route completion must be handled cleanly

The map/navigation UI must clearly show maneuvers such as:

Preserve the visual maneuver information supplied by Google Navigation SDK.

==================================================
KENTAS NAVIGATION SPEECH
==================================================

Kentas must not sound like default formal navigation.

Navigation instructions must remain short, accurate, and safe, but phrased naturally in Lithuanian.

Examples of tone:

- “Nu davai, po šimto metrų sukam į dešinę.”
- “Tuoj kairė, nepražiopsok.”
- “Varom tiesiai.”
- “Žiede imam antrą išvažiavimą.”
- “Biški prašovėm, apsisukam, kai bus galima.”
- “Nu va, beveik atvarėm.”

Important rules:

- the actual maneuver, direction, distance, and exit number must never be changed
- humor must not hide or delay the instruction
- instructions must not become long monologues
- do not call OpenAI for every navigation instruction
- create a deterministic/local phrase formatter using the maneuver data from the navigation SDK
- support phrase variation so the exact same sentence is not repeated every time
- avoid offensive slurs or instructions that encourage unsafe driving
- Kentas may be funny, but navigation clarity always has priority

==================================================
NAVIGATION AUDIO PRIORITY
==================================================

Navigation instructions always have priority over casual conversation.

If a maneuver instruction becomes urgent while Kentas is speaking conversationally:

1. safely stop or pause the conversational TTS
2. speak the navigation instruction
3. do not lose or stop the active route
4. conversation may continue afterward only if the conversation session is still active

Prevent overlapping TTS voices.

Use one centralized speech/audio coordinator rather than unrelated TTS calls from multiple classes.

==================================================
KENTAS CONVERSATION
==================================================

There must be one clearly visible Kentas/microphone button.

On press:

- open the Kentas conversation interaction
- begin a single SpeechRecognizer listening request
- show a simple visible state such as listening / thinking / speaking
- send valid recognized speech to the existing AI service
- speak the AI response through TTS
- listen again only while the conversation remains active
- reset the 30-second inactivity timer whenever:
  - user speech begins
  - a valid speech result arrives
  - the user manually interacts with the conversation

If no user speech occurs for 30 seconds:

- stop SpeechRecognizer
- cancel pending recognizer restarts/callbacks
- close the conversation state
- return to navigation-only behavior
- do not stop navigation
- do not announce a verbose “mode changed” message

Recoverable recognizer errors must not create an infinite restart loop.

Recommended simple behavior:

- one controlled retry for a temporary recognizer failure while the conversation is still active
- if it fails again, close listening cleanly and keep navigation running
- the user can press the Kentas button again to retry

Do not automatically reopen conversation after it has timed out or been closed.
